# Decisions — LR-20260920-DVCC-003

## Human-approved (Task Packet revision 1)

- Japanese is the default UI language; English is selectable; the choice survives a restart.
- Every future user-facing feature ships in both languages in the same PR; a missing translation is a Required Fix, never Quality Debt.
- Persisted values (Review State, Resource State, Freshness, event types, schema fields, file names, error codes) stay language-neutral.
- No external translation API, no network, no LLM translation: the resources live in the repository.
- Phase 3 does not start until this foundation is merged.

## Implementation decisions

| ID | Decision | Rationale |
|---|---|---|
| L3-001 | A small typed localization layer in `src/i18n/` with no new dependency: `ja.ts` defines the key set, `types.ts` derives `TranslationKey` from it, and `en.ts` is typed as a full record of those keys. A missing or extra key in either dictionary is a **compile error**, and a runtime parity test covers blanks and duplicates as well. | The Task Packet asks for a small typed layer and prefers a custom implementation. Deriving the key type from one dictionary makes the compiler the first parity gate, so a forgotten translation cannot reach a test run, let alone a review. |
| L3-002 | Keys are stable identifiers in dotted form (`review.actions.start`, `freshness.aligned`, `errors.saveConflict`); parameters are named placeholders (`{name}`) substituted by `t(key, params)`. No ICU, no pluralisation engine; where a count matters the two languages get their own wording. | English sentences as keys break as soon as the English changes, and an internal enum as display text is exactly what this phase removes. Named placeholders keep Human content out of the translation files. |
| L3-003 | The preference is persisted as `<data root>/settings.json` (`{"schemaVersion": 1, "locale": "ja"}`) through a **new `settings` storage target** in Rust, reusing the existing atomic write, `.bak` and precondition machinery. It is written only when the Human changes the language. | §10 asks for a local-first explicit contract separate from project / review data. Reusing the storage boundary keeps the data-root confinement and recovery behaviour of Phase 1 instead of introducing a second file-writing path. |
| L3-004 | Missing `settings.json` → Japanese, silently (a fresh install is the normal case). Unreadable or invalid content → Japanese **plus a visible warning**, and the file is left untouched: no project or review data is read or written on that path. | The packet's fail-safe rule. Leaving the unreadable file alone matches Phase 1's "never overwrite what we could not read". |
| L3-005 | Display labels leave the domain: `REVIEW_STATE_LABELS`, `RESOURCE_STATE_LABELS`, `RESOURCE_STATE_HINTS`, `FRESHNESS_LABELS`, `GIT_STATUS_LABELS` and the Freshness explanation sentences become translation keys (plus parameters for the two HEAD values). `src/domain/*` keeps the values and the logic, not the words. | L10N-08 and the neutrality rule: the domain must not carry a language. It also removes the risk of a label being persisted by accident. |
| L3-006 | `buildReviewRequest` takes the locale and emits a Japanese or English request; the data it interpolates is identical in both. Existing `request-r<N>.md` files are never rewritten by a language change — only a new "Copy review prompt" uses the current locale. | §18: the artifact is Human-visible text, so it follows the UI language, but rewriting saved artifacts would break the latest-wins contract and touch data the Human owns. |
| L3-007 | Against new hard-coded text: the documented rule ("user-facing strings live in `src/i18n`"), the compile-time key type, the parity test, and a small static test that scans `src/app`, `src/components` and `src/features` for literal text in JSX and in the usual attributes (`title`, `placeholder`, `aria-label`) with a short allowlist. | §22 asks for something practical rather than a large scanner; the four layers together make a forgotten string fail a check without flooding the run with false positives. |
| L3-008 | Timestamps are formatted per locale for display only; the stored value stays ISO-8601 UTC. `document.documentElement.lang` follows the locale. | §20 / §26; the data contract keeps its single timestamp format. |
| L3-009 | The **review-type suggestion list** is UI chrome and is localized (`PR review` / `PRレビュー`, …); the value the Human picks or types is stored verbatim and is never translated afterwards, including when it is emitted into a review request. | The list is a convenience shown in a datalist; the moment a value is chosen it is Human content (§19). Localizing the suggestions gives a Japanese user Japanese defaults without any mechanism that rewrites stored data. A session created in one language therefore keeps its recorded type — which is correct, because that string is what the Human decided. |
| L3-010 | The **pre-filled checkpoint text** in the suspend dialog is localized; `checkpoint.md` keeps whatever the Human saved, and a later language change never rewrites it. | It is a draft the Human edits before saving, so it is UI text at the moment it is offered and Human content once saved. |
| L3-011 | **Event notes** written to `events.jsonl` stay exactly as they are (unchanged wording, no schema change). In the UI the event **type** gets a localized label and the note is shown as technical detail next to it. | Translating stored notes would change historical file content and leave old files in the old language; the type is the part that carries meaning for a Human reading the history. Backwards compatibility with existing data is an Acceptance Criterion (L10N-12). |
| L3-012 | Every place that renders a raw enum as visible text (resource badge and segmented control, resource radios, verdict in a toast and in the previous-result line, event type in the history) is changed to look up a localized label; the enum value itself, its CSS class fragment and its `data-state` attribute are untouched. | L10N-08 plus the neutrality rule: the value is data, the label is language. The `data-*` attributes stay literal so the existing UI smoke keeps working. |
| L3-013 | Rich messages (ten of them, with `<strong>` / `<code>` / `<kbd>` inside the sentence) use a small helper that splits a translated template on `{placeholder}` and substitutes React nodes, so the sentence stays one translatable unit and the markup stays in the component. | A translator must be able to move the emphasised part inside the sentence, which Japanese word order requires; splitting the sentence across JSX children — what the code does today — makes that impossible. |
| L3-014 | Every sentence currently assembled from fragments in JSX becomes a single parameterised message (queue row, detail header, "from {state}", "· {n} reviews", "Earlier results of R{n} kept: {files}", the unreadable-review heading and its two bodies). | Concatenation encodes English word order; Japanese needs the parts in a different place. |
| L3-015 | `describeHealthProblem` stops returning an English sentence fragment and returns a structured problem (a key plus parameters); the three call sites render it through `t`. | The fragment is spliced into three different grammatical contexts, which no translation can satisfy at once. |
| L3-016 | `t` takes an optional `count`: when a key has a `_one` variant it is used for `count === 1` in English; Japanese defines a single form. | The three pluralisation hacks in the code are English-only and silently wrong for 1 in one case. |
| L3-017 | Locale-dependent punctuation (the `—` placeholder, `…`, `·`, `→`, `∅`, quotes, the resource-tooltip joiner) is part of the translated strings rather than hard-coded in components, except for glyph-only buttons (`×`) and separators that carry no language. | It is the cheapest way to let Japanese use `：` and full-width punctuation where that reads better, without a separate formatting layer. |
| L3-018 | `settings.json` is read only at `schemaVersion === 1`; a missing, mistyped, `0` or later version makes the file invalid (Japanese plus the existing warning) and loading still never writes, so the file survives for whichever version owns it. | A version field that is not checked is decoration: it would let a later layout be read as if its fields meant what this version reads them as. Refusing costs one preference; guessing could silently mean the wrong language or, later, the wrong setting. |
| L3-019 | The language switch follows the choice at once but commits it only if the write succeeds: a failed write puts the interface back to the language that is still stored and shows a localized error, unless a newer choice has already superseded it. | A preference the interface shows but the file does not hold would come back changed at the next start-up, which is exactly what the restart requirement forbids. Rolling back keeps the screen and the file saying the same thing; the error makes the failure visible instead of swallowing it. |
| L3-020 | Preference writes are serialized per storage backend (one `createSerialQueue` per backend, held weakly), and `saveLocale` itself is the serialized entry point rather than the store. | Rapid switching issues overlapping writes whose completion order is not the order they were made, so the last choice could be overwritten by an earlier one. Serializing at the function makes that true for every caller, not only the one that goes through the store. No new dependency: the queue already exists for the review hub. |
| L3-021 | Text produced outside React — validation, transition guards, service failures, file-health problems and recovery notices — becomes a `Message` (`src/domain/message.ts`): a translation key plus parameters, rendered by `translate(t, message)` at the interface. The key is typed against the dictionaries through a types-only import, so an unnamed message is a compile error and no dictionary reaches the domain at runtime. | These layers have no access to a React context, and passing a translator into the domain would put a language in it. A named message keeps the domain deciding *what* is wrong and the interface deciding *how it reads*, and it keeps the compile-time parity gate. |
| L3-022 | A `Message` may carry other messages as parameters (`messageParams`), used for the recovery notices where the file label is itself translated. | `"{label} was restored…"` needs the label in the same language, and the label differs per file; nesting keeps one sentence per notice instead of four. |
| L3-023 | Technical detail inside a localized sentence stays literal: schema parse reasons (they name schema fields), storage error codes and messages from Rust, the action type in a guard message, event notes, and file names. | The same rule as L3-011: the frame is language, the detail is data. Translating a schema reason would mean translating the schema; translating a storage code would break the one string an operator can search for. |
| L3-024 | The queue carries the unreadable-review problem as a `Message` (`QueueSource.problem`), not as a rendered string. | The queue is built in the domain, where there is no language; rendering it in the row keeps the file-health wording in one place. |

# Decisions — LR-20260920-DVCC-002

## Human-approved (Task Packet revision 1)

- Phase 2 observes **local** Git facts only: no GitHub API, no network Git operation, no `fetch` / `pull` / mutation of any kind.
- `GitObservation` is runtime memory only in v0.2; after a restart the state is `UNKNOWN` until the Human refreshes.
- Freshness is derived, informational state with a fixed priority (WORKTREE_DIRTY > REVIEW_STALE > HEAD_CHANGED > ALIGNED > UNKNOWN) and must never change Review State.
- No automatic refresh at app startup; Refresh All runs sequentially.
- The Phase 1 local-folder boundary (F-9) is reused, not weakened or duplicated.

## Implementation decisions

| ID | Decision | Rationale |
|---|---|---|
| L2-001 | The Git observation lives in a new Rust module `src-tauri/src/git.rs` exposed as a single `#[tauri::command]`. It calls `launcher::validate_project_folder` (sync, free-standing, returns the canonicalized local `PathBuf`) for the path boundary instead of re-implementing it, and runs `git` through `std::process::Command` with `current_dir(resolved)` — never a shell, never user input on a command line, no generic executor. | Task Packet §4.3 / §4.5. `validate_project_folder` already performs the whole F-9 boundary (UNC / prefix / drive type / link-target / canonicalize) and needs no `State` or `AppHandle`, so reuse keeps one implementation of the boundary. `current_dir` removes the last place a path could be interpreted as an argument. |
| L2-002 | Bounded timeout: one deadline shared by all git invocations of a single observation (default 5 s, taken from `contract/limits.json` so Rust and TypeScript read one source). The child is spawned with piped output drained by reader threads while the parent polls `try_wait`; on deadline the parent kills **that `Child` handle only** and returns `TIMEOUT`. | The repository has no child-process or timeout helper to reuse (Phase 1 spawns no processes). Draining the pipes prevents a full-buffer deadlock on a large `git status` output; killing the handle guarantees only this observation's PID is affected (never a kill by process name). |
| L2-003 | `observedAt` (ISO-8601 UTC) is produced in Rust with a small dependency-free formatter and unit-tested against known epochs, rather than added on the TypeScript side. | The timestamp is a property of the observation, so it belongs where the observation happens; the crate has no `chrono` / `time` dependency and adding one for a formatter would widen the dependency surface for no benefit. |
| L2-004 | The observation is held in React state only — a `Record<projectId, GitObservation>` slice in `appState` — and never passes through `StorageBackend`, the session schema or `contract`-owned files. | Task Packet §4.7: the current Git fact is volatile and a cache could be mistaken for a current fact. Keeping it out of `parseSessionFile` / `serializeSession` also avoids a Phase 1 persistence schema migration. |
| L2-005 | Freshness derivation is a pure TypeScript module (`src/domain/…`), verified by an independent literal oracle table in `src/test/` in the style of `src/test/transitionContract.ts`, plus a contract test that cross-checks every row against the implementation. UI behaviour is verified by a scratch CDP smoke run instead of component tests. | Vitest runs in the `node` environment and only matches `src/**/*.test.ts` (no jsdom, no testing-library), so UI components cannot be unit-tested in this repo; the logic must therefore live in a `.ts` module, and the oracle must not import the implementation it checks. |
| L2-006 | DVCC reuses the Development Dashboard's **separation idea** (live facts vs. Human-confirmed state vs. derived freshness computed only by deterministic comparison) but keeps the Human-specified five-state vocabulary (ALIGNED / HEAD_CHANGED / REVIEW_STALE / WORKTREE_DIRTY / UNKNOWN) rather than the Dashboard's `ALIGNED / GITHUB_AHEAD / UNKNOWN / NOT_APPLICABLE`. | The Dashboard contract governs a different repository and a GitHub-sourced comparison; its class-A "live fact" definition is about fresh GitHub reads, which Phase 2 deliberately does not perform. The shared principles that are adopted: derived freshness is computed, never inferred; unknown inputs yield UNKNOWN rather than a guess; observed facts never overwrite Human-recorded state. |
| L2-007 | Phase 2 is started on the Human's explicit authorization even though the vault still records `Current Phase: Phase 0` and Phase 1 as `PLANNED / NEXT`. The stale vault text is not edited; it is reported back as a Documentation Sync candidate. | `05_LLM_IDE_Instructions.md` makes "expanding the architecture scope into Phase 2 or later" a Human Gate item **and** fixes the canonical source order as Human instruction → fresh repository state → … → vault, with the explicit rule that stale documentation must not be treated as canonical when it conflicts with fresh repository state. The Human authorized Phase 2 directly in this campaign's instruction, and the repository shows Phase 1 merged at `f557aa6`; both canonical sources agree, so the gate is satisfied and no STOP is required. |
| L2-008 | Reuse Scan / Adoption Decision: no new dependency is adopted for Phase 2. The local-path boundary is reused from `launcher.rs`, the command / error / port / state patterns from Phase 1, the shared-constant mechanism from `contract/limits.json`, and the *separation principle* (observed facts vs. Human-recorded state vs. derived comparison) from the Development Dashboard Data Contract. Git is invoked as an external CLI that is already a prerequisite of the workflow; no Git library crate is added. | The project's reuse rule prefers an existing internal contract over a new dependency, and the Task Packet forbids widening the boundary. A Git library crate would add a large dependency surface (and its own filesystem behaviour) for facts that four read-only CLI calls already provide; the CLI is invoked without a shell and only with read-only subcommands. |
| L2-009 | Clarification of the "no persistence" rule: only the **observed** facts (`status`, `head`, `branch`, `detached`, `dirty`, `observedAt`) are runtime-memory-only. The Human-recorded `expectedHead` / `reviewedHead` remain persisted exactly as in Phase 1, and `REVIEW_STALE` is computed from the persisted reviewed HEAD versus the in-memory observed HEAD. | The roadmap requires `REVIEW_STALE` and restart-survival of the review session, which is only possible if the recorded HEADs persist; the volatility argument applies solely to the observation. Recording this explicitly prevents a later reader from concluding that Phase 2 contradicts D-007 or the Phase 1 acceptance criteria. |
